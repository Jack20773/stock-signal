## 先給結論：此計畫可行，但目前不能直接做「錯字表全域替換」

目前最危險的誤解是：有 687 集官方稿，就能自動學出可靠的「錯→對」表，然後取代官方來源。

**不成立，原因有三個：**

1. **官方稿尚未證實是人工正確稿。**它目前只能是「silver label」，不是 gold label。
2. **純文字後處理無法可靠判斷同音歧義。**例如使用者明確指出「某集真的講『奇虹』」的可能；看到 `奇虹` 時，系統不能僅憑文字知道該改成 `奇鋐`。
3. **你現在把 SRT 轉成無時間軸的 `.md`，丟掉了最有價值的消歧證據。**後續若要針對可疑詞重新解碼音訊，沒有時間軸會很痛苦。

因此，目標不應是「建立全域錯字替換表」，而應是：

> 建立一個**保守的實體辨識／校正層**：能安全正規化的才自動修；有歧義的股票名則保留候選、重新解碼或送入低頻人工驗證；用獨立保留集證明其在「股票實體與訊號」層級達標。

# 1. 對齊方法

### Finding 1.1 — 段落級 `difflib` 不適合作為訓練資料對齊器
- **嚴重度：major**
- **證據：**
  - 已知結果為「段落層級相似度 88.34%，但只回報 1 個 diff block」。
  - `srt_to_md()` 已將 `.srt` 轉成「純文字段落 `.md`（無時間軸）」。
- **影響：**
  - 段落切法不同時，演算法會把後面大段內容視為一個 replace 區塊。
  - 無法取得可信的「官方字串 A 對應到本地字串 B」細粒度配對。
  - 無時間軸時，日後無法可靠回到音訊重跑特定片段。
- **具體修法：**
  - 保留原始 SRT，不可只留 `.md`。
  - 對齊單位改為「整集文字的字元級對齊」，但採取**分層對齊**，不要直接對兩個約兩萬字字串做裸 `difflib`。

### 建議對齊流程

#### A. 保存三份資料，而非只保存 `.md`

每集至少保存：

```text
raw_official_text          # 官方原文，不覆寫
raw_independent_srt        # faster-whisper 原始輸出，含 start/end
independent_segments.json  # 每個 SRT segment 的文字與時間軸
normalized_official_text
normalized_independent_text
```

`normalized_*` 僅供比對，不可覆蓋 raw text。

#### B. 建立「可追溯」的正規化函式

只做低風險、可逆或可記錄的處理：

- 全半形統一。
- 多餘空白、換行統一。
- 標點統一或在比對時忽略。
- `KY`、`-KY`、`－KY` 的格式標準化。
- 阿拉伯數字格式統一，例如 `0050` 保留為字串，不轉成中文數字。
- `台` / `臺` 可建立「比對用等價規則」，但 raw text 必須保留。

不要一開始做這些事：

- 不要把所有同音字轉成同一字。
- 不要把所有 `台` 直接替換成 `臺`。
- 不要移除所有中文常用詞；會破壞對齊上下文。

正規化函式的輸出應保留原始索引映射：

```python
NormalizedText(
    text="...",
    normalized_index_to_raw_span=[...],
)
```

否則找到差異後無法回報原文位置。

#### C. 先找高可信錨點，再做局部字元級動態規劃

不建議先做中文斷詞。此問題核心是股票名、人名、代碼、連字號，中文斷詞反而會加入額外誤差。

建議流程：

1. 對兩份正規化全文找共同的長字串 n-gram。
   - 建議初始長度：8～15 個中文字元／字元。
   - 忽略出現太多次的常見 n-gram。
   - 只採用順序單調的錨點鏈。
2. 將兩個錨點中間的區段切成局部對齊窗。
3. 在每個局部窗內使用字元級全域序列對齊：
   - Needleman–Wunsch / edit-distance 類演算法。
   - 需要支援 insertion、deletion、substitution。
   - 標點與空白的成本設低或為 0。
   - 一般中文字替換成本為 1。
   - 不建議一開始就把同音字替換成本設得太低，否則會把不相干片段硬對上。
4. 每個差異 span 產生：
   - 官方原文 span。
   - 本地 ASR 原文 span。
   - 前後各 20～50 字上下文。
   - 對齊品質分數。
   - 對應的 SRT segment ID 與時間範圍。

對齊結果應類似：

```json
{
  "episode": 687,
  "official_span": "貿聯-KY",
  "local_span": "茂林KY",
  "official_context": "……貿聯-KY、奇鋐、智邦……",
  "local_context": "……茂林KY、奇虹、智邦……",
  "local_time_range": [1234.2, 1241.8],
  "alignment_confidence": 0.96
}
```

#### D. 對齊品質要可拒絕

以下情況不得產生「錯→對」訓練樣本：

- 局部窗太大且沒有足夠錨點。
- 前後上下文對齊差。
- 官方與本地文字長度差過大。
- 同一官方 span 對到多個遠距離本地 span。
- 本地片段時間範圍異常長。
- 音訊版本、片頭片尾、廣告段落疑似不同。

這些資料應標記為 `alignment_uncertain`，不是硬塞進錯字表。

# 2. 雜訊過濾：如何只抽專有名詞錯誤

### Finding 2.1 — 把所有 diff 視為 ASR 錯誤會污染資料集
- **嚴重度：critical**
- **證據：**
  - 使用者已明確指出：「官方稿本身可能經過人工／LLM 潤稿，兩邊差異不全是聽錯。」
  - 差異中包含口語贅詞、標點、同義改寫。
- **影響：**
  - 若把「語句潤稿差異」學成 ASR 錯誤，校正器會把本地逐字稿改得更不像音訊。
  - 後續若用這些資料微調模型，會把模型訓練成追隨官方的編輯風格，而不是提升聽寫正確率。
- **具體修法：**
  - 差異抽取必須以「官方實體 mention」為中心，而不是以全部 diff 為中心。
  - 官方稿只能當弱監督資料；高影響實體必須有人工聽音驗證集。

### 建議的雜訊過濾規則

#### A. 先建立可列舉的股票實體目錄

目前 `stock_dict.py` 只有：

```text
resolve()
resolve_code()
```

### Finding 2.2 — 現有 `stock_dict.py` 無法支援完整實體比對
- **嚴重度：major**
- **證據：**
  - 已明確說明「沒有現成的股票名稱清單可直接拿來用」。
- **影響：**
  - 無法掃描官方稿中有哪些股票名稱。
  - 無法判斷一個錯字是否可能是股票名稱誤聽。
  - 無法評估股票實體 precision / recall。
- **具體修法：**
  - 在 `stock_dict.py` 或新模組提供可列舉、可版本化的實體資料：

```python
StockEntity(
    code="3661",
    canonical_name="世芯-KY",
    aliases=["世芯", "世芯KY", "世芯-KY"],
    market="TW",
)
```

至少提供：

```python
iter_stock_entities()
get_stock_alias_index()
resolve_text_to_candidates(text)
```

不可用「對所有可能字串呼叫 `resolve()`」的方式硬湊，因為不可控、難測試，也難處理別名與歧義。

#### B. 只從官方稿中已辨識出的實體 mention 建立候選

流程：

1. 用股票名稱、代碼、別名詞典掃描官方稿。
2. 對每個官方股票 mention 找其字元級對齊到的本地 span。
3. 僅在下列條件成立時，建立候選誤聽配對：
   - 官方 span 能唯一連到一檔股票。
   - 局部對齊品質達標。
   - 本地 span 與官方 span 不相同。
   - 本地 span 不只是標點／格式差。
   - 本地 span 位於合理的對齊範圍內。
4. 將候選分級，而不是直接採用。

建議分類：

| 類別 | 例子 | 是否可自動處理 |
|---|---|---|
| 格式／異體字 | `臺積電 → 台積電`、`貿聯KY → 貿聯-KY` | 可高信心正規化 |
| 單一已知誤聽 | `奇虹 → 奇鋐` | 需歧義檢查 |
| 多字同音誤聽 | `茂林KY → 貿聯-KY` | 預設不可直接替換 |
| 官方潤稿差異 | 贅詞、省略、重述 | 排除 |
| 人名／節目名 | `古來 → 股癌`、`聖夢公 → 謝孟恭` | 與股票分開管理 |

#### C. 不要把人名、節目名、股票名混成同一校正表

原因：

- 股票名的錯誤會直接造成錯誤訊號與錯誤代碼。
- 人名／節目名主要影響文本品質與 prompt 上下文。
- 同一錯字字串在不同類別可能有不同修正結果。

建議實體類型至少分為：

```text
stock
stock_code
person
show
organization
domain_term
```

# 3. 校正表形式與誤傷風險

### Finding 3.1 — 全域「錯→對」字串 replace 必然造成誤傷
- **嚴重度：critical**
- **證據：**
  - 使用者已提出反例：「某集真的講『奇虹』」。
  - 範例中存在 `貿聯-KY → 茂林KY` 這種多字誤聽與格式混雜情況。
- **影響：**
  - 系統可能把正確提到的名稱改成另一檔股票。
  - 這類錯誤比漏抓更危險：下游 Gemini 會非常自信地分析一檔根本沒被提到的股票。
- **具體修法：**
  - 不建立無條件的 `wrong_text -> correct_text` 全域替換。
  - 改成「具備證據、條件與信心分數的實體校正規則」。

### 建議資料結構

```json
{
  "rule_id": "stock-confusion-00017",
  "asr_model_fingerprint": {
    "model": "large-v3-turbo",
    "faster_whisper_version": "1.2.1",
    "ctranslate2_version": "4.8.0",
    "decode_config_hash": "..."
  },
  "observed_text": "奇虹",
  "target_entity_type": "stock",
  "target_entity_id": "canonical-stock-id",
  "target_canonical_text": "奇鋐",
  "evidence": {
    "episode_count": 12,
    "occurrence_count": 19,
    "human_verified_count": 6,
    "alignment_confidence_mean": 0.97
  },
  "collision_risk": "high",
  "apply_policy": "candidate_only",
  "status": "approved"
}
```

### 校正規則必須區分三種套用策略

#### 1. `safe_normalize`：可自動套用

適用於：

- 全半形。
- `-KY` 格式。
- 已確認不會改變實體語意的別名。
- 公司慣用字形，例如專案明確規定公司 canonical 名稱用 `台` 或 `臺`。

範例：

```text
貿聯KY -> 貿聯-KY
臺積電 -> 台積電
```

前提是這些都是同一個已辨識出的股票實體，而不是對全篇 raw text 盲改。

#### 2. `entity_link_only`：不改原文，只補 canonical entity

適用於：

- `奇虹` 被高度懷疑是 `奇鋐`，但仍有同名或語境衝突風險。
- 文本保留 `奇虹`，但在結構化結果中記錄：

```json
{
  "raw_mention": "奇虹",
  "candidate_entities": ["奇鋐"],
  "entity_confidence": 0.91,
  "source": "asr_confusion_rule"
}
```

這能讓下游分析使用 canonical entity，同時保留可追查原文。

#### 3. `candidate_only / abstain`：預設拒絕自動修正

適用於：

- 多字同音誤聽。
- 可能對應多檔股票。
- 錯字本身可能是正常詞。
- 證據樣本太少。
- 不同版本模型的誤聽行為不同。

這類案例應：

1. 保留原始文字。
2. 留下候選股票。
3. 以 SRT 時間範圍重跑局部音訊。
4. 若仍無法判斷，標記為低信心，不餵成確定訊號。

### 上下文條件能降低風險，但不是充分證據

可以用的條件：

- 前後 N 字是否出現股票討論語境，例如價格、財報、供應鏈、買賣、法說等詞。
- 同一段是否還提到其他股票代碼／公司名。
- 是否有「這檔」、「公司」、「股票」等語境。
- 是否有候選股票的代碼同時出現。
- 是否是主持人、來賓、廣告、片頭等段落。

但必須明確：

> 上下文只能提高或降低信心，不能從根本解決同音歧義。

真正可用來消歧的資料仍是音訊、時間軸、重新解碼與人工抽驗。

# 4. 後處理 vs `initial_prompt` / hotwords

### Finding 4.1 — 只依賴後處理無法修正所有關鍵錯誤
- **嚴重度：major**
- **證據：**
  - `貿聯-KY → 茂林KY` 不只是格式問題，而是聲學辨識錯到另一個詞。
  - 目前本地稿在一次點名五檔時，只能正確識別 `0050`、`智邦`。
- **影響：**
  - 純文字替換只會修正「已知、固定、低歧義」錯誤。
  - 沒有出現在錯字表的新股票、新人名、新產業術語仍會失敗。
- **具體修法：**
  - 採用「保守後處理 + 小範圍重解碼提示」雙軌。
  - 不要把所有股票名一次塞進 prompt。

### Finding 4.2 — 大型股票名單塞入 `initial_prompt` 會增加幻覺與偏誤
- **嚴重度：major**
- **證據：**
  - 使用者已正確擔心：「initial_prompt 會不會誘發幻聽、把沒講的股票名塞進來」。
  - 股票宇宙通常遠大於單集實際會出現的股票數。
- **影響：**
  - 模型可能將模糊音訊偏向 prompt 中的股票名。
  - 本來沒有提到股票的段落，可能被偏置成某檔股票。
  - prompt 過長還可能稀釋真正重要提示。
- **具體修法：**
  - 對 `initial_prompt` 與 hotwords 做 A/B benchmark，不可未測即上線。
  - 使用小型、分層提示詞典，不要放完整市場股票清單。

### 建議取捨

| 方法 | 適合用途 | 優點 | 主要風險 |
|---|---|---|---|
| 事後安全正規化 | 台/臺、KY 格式、代碼格式 | 高可控、低成本 | 修不了未知誤聽 |
| 實體候選／校正規則 | 已知且有多集證據的誤聽 | 可改善常見錯字 | 同音歧義誤傷 |
| `initial_prompt` | 節目名、主持人名、少量固定術語 | 可改善固定專名起點 | 長清單造成偏置 |
| hotwords | 少量候選股票的局部重解碼 | 對疑難 span 有機會改善 | 可能誘發不存在的名稱 |
| 微調模型 | 長期改善聲學與專名辨識 | 真正改善 ASR 能力 | 需要可靠標註、訓練流程與驗證 |

### 建議實作方式

#### 第一輪轉錄

使用簡短、固定的 prompt，只放極穩定且常見的名稱，例如：

- 節目名稱。
- 主持人姓名。
- 少量已人工驗證的固定術語。

不要放完整股票清單。

#### 第二輪局部重解碼

只有在以下情況觸發：

- 本地稿出現已知高風險誤聽字串。
- 實體 linker 有高分候選但不確定。
- 對齊／歷史資料顯示該錯誤常發生。

對該 SRT 時間範圍前後各加幾秒 buffer，使用**少於 5～10 個**候選詞重跑，並比較：

- 原始轉錄。
- 不加 prompt 的局部重跑。
- 加候選詞的局部重跑。

只有多個結果一致、且實體判定信心提升時才採用。

### 關於 `faster-whisper` 支援

你提供的資訊只足以確認 `transcribe.py` 目前沒有把 `initial_prompt` / hotwords 暴露出來，不能直接假設現有呼叫介面已正確支援所有參數。

執行任務應包含：

1. 檢查目前 `faster-whisper 1.2.1` 的實際 `WhisperModel.transcribe()` 參數。
2. 在 `transcribe.py` 加入顯式設定欄位。
3. 將 decode config、prompt、hotwords 記入每集 metadata。
4. 建立相同音訊的 A/B 測試，量化：
   - 股票實體 recall。
   - 股票實體 precision。
   - 假股票 mention 數。
   - 非股票文字錯誤率變化。

### 額外挑戰：這不是「訓練 Whisper」

### Finding 4.3 — 錯字表與 prompt 不等於訓練模型
- **嚴重度：major**
- **證據：**
  - 現有資源是 `faster-whisper` / CTranslate2 推論管線。
  - 使用者目標描述為「練到夠準」。
- **影響：**
  - 若只做 prompt 和 replace，模型本身不會學會新的聲學對應。
  - 更換模型版本、decode 參數、VAD 設定後，錯字規則可能失效。
- **具體修法：**
  - 將「規則校正」與「模型微調」視為兩條不同路線。
  - 若後續真的要訓練，需使用可訓練的原始 Whisper/Hugging Face 流程，再轉回 CTranslate2 推論格式。
  - 在官方稿品質驗證前，不要用全部官方稿直接微調；否則會把官方稿錯誤與潤稿風格一起學進模型。

所有錯字規則都必須綁定：

```text
模型版本 + faster-whisper 版本 + CTranslate2 版本 + 語言設定 + decode 參數 + prompt 策略
```

你目前已知版本是：

```text
large-v3-turbo
faster-whisper 1.2.1
ctranslate2 4.8.0
condition_on_previous_text=False
```

任何一項改動後，都要重新跑保留集。

# 5. 「夠準可以取代官方站」的判準

### Finding 5.1 — 字元相似度不具業務意義
- **嚴重度：major**
- **證據：**
  - EP687 的整體內容完整度甚至是本地稿多 1.2%。
  - 相似度 88.34%，但訊號最密集段落五檔股票只正確兩檔。
- **影響：**
  - 高字元相似度可能仍漏掉最重要的股票訊號。
  - 以 WER 或字元相似度當唯一門檻，會製造錯誤安全感。
- **具體修法：**
  - 用「股票實體」與「訊號」兩層指標做 release gate。

### Finding 5.2 — Gemini 對 Gemini 的一致性不是正確性證明
- **嚴重度：major**
- **證據：**
  - 下游使用 `gemini-flash-lite-latest`。
  - 計畫中的想法是兩份稿各跑 Gemini，比較股票與方向一致性。
- **影響：**
  - 同一個模型可能對兩份不同文本產生相同錯誤。
  - `latest` 類模型別名未必永久固定，跨日期比較可能不可重現。
  - 一致只能證明「下游輸出一致」，不能證明「內容真實正確」。
- **具體修法：**
  - Gemini 一致率可作為端到端 proxy，但不可作為唯一上線標準。
  - 每次評估記錄 prompt、模型識別資訊、輸入文本 hash、輸出 JSON。
  - 對 Gemini 不一致或高影響個案做人工聽音裁決。

### 建議四層指標

#### Layer 1：基本轉錄完整性

便宜，但只能當健康檢查：

- 音訊時長覆蓋率。
- SRT segment 是否有大空洞。
- 字數比例。
- 開頭、結尾錨點是否存在。
- 異常短集／異常長集比例。

不應當品質門檻主指標。

#### Layer 2：股票實體辨識品質

以「每次股票 mention」為單位，而不是以整集為單位：

```text
Entity precision = 正確辨識的股票 mention / 系統辨識出的股票 mention
Entity recall    = 正確辨識的股票 mention / 基準稿中的股票 mention
Entity F1
```

另計：

- 股票代碼正確率。
- 公司名到股票代碼的 linking 正確率。
- 假股票率：本地稿多出、但人工確認音訊沒有提到的股票 mention。
- 高風險校正誤傷率。

對股票訊號系統而言，**precision 通常比 recall 更重要**；憑空新增一檔股票比漏掉一檔更危險。

初始建議 release SLO：

| 指標 | 建議最低門檻 |
|---|---:|
| 股票 mention precision | ≥ 99% |
| 股票 mention recall | ≥ 95% |
| 股票代碼／canonical linking accuracy | ≥ 99% |
| 高風險自動校正誤傷 | 0 件 |
| 不確定實體被錯當確定訊號 | 0 件 |

這些門檻應在**人工聽音驗證的保留集**上計算，不是在用來建立規則的資料上計算。

#### Layer 3：極性／訊號代理指標，不需 Gemini

建立簡單的本地規則評估，而非嘗試取代 Gemini：

- 先從官方稿找出股票 mention。
- 在同一局部窗口找方向詞與語境詞。
- 比較本地校正稿能否找回：
  - 同一股票。
  - 同一 mention 區段。
  - 同一方向詞窗口。

這是便宜 proxy，不要求它完整理解語義，只用來量測「股票名錯誤是否導致訊號窗口消失」。

#### Layer 4：Gemini 端到端驗證

只在每輪候選方案完成後跑，不需每次改規則都跑全量。

比較：

```text
官方稿 -> Gemini -> 股票、方向、理由
本地校正稿 -> Gemini -> 股票、方向、理由
```

建議評估：

- 個股集合 exact match。
- 個股集合 precision / recall。
- 相同股票的方向一致率。
- 高信號等級項目的方向一致率。
- 本地多出虛假訊號的比例。
- 官方有、本地漏掉的訊號比例。

建議初始門檻：

| 指標 | 建議門檻 |
|---|---:|
| 個股集合 precision | ≥ 98% |
| 個股集合 recall | ≥ 95% |
| 同股票方向一致率 | ≥ 97% |
| 高影響案例人工裁決正確率 | ≥ 99% |

這些不是保證值；最終門檻應由「錯一檔假訊號可接受程度」決定。

### 統計提醒

若要以 95% 信心水準證明「實際 precision 至少約 99%」，而測試中沒有任何錯誤，粗略需要約 **300 個彼此足夠獨立的已驗證股票 mention**。這只是最低量級；同一集內的錯誤往往相關，所以不能把同一段連講 20 檔完全當成 20 個獨立樣本。

# 6. 抽樣策略：跑幾集、怎麼選

### Finding 6.1 — 現有 5 組配對不足以建立或驗證規則
- **嚴重度：major**
- **證據：**
  - 現有配對僅 EP681–684 與 EP687。
  - 這些集數相近，語言習慣、主持人、當期市場熱門詞高度相關。
- **影響：**
  - 很容易只學到最近幾集重複出現的股票。
  - 對歷史用語、不同來賓、不同錄音品質、新股／舊股名稱沒有代表性。
- **具體修法：**
  - 按「時間 + 股票 mention 密度 + 音訊／節目型態」分層。
  - 在寫任何錯字規則之前，先鎖定保留集，避免評估洩漏。

### 建議資料切分

以 episode 為切分單位，不能同一集的一半當訓練、一半當測試。

建議先將 687 集分為：

| 集合 | 比例 | 用途 |
|---|---:|---|
| Train | 約 60% | 挖掘誤聽規則、調整 prompt |
| Validation | 約 20% | 調參、決定規則門檻 |
| Locked test | 約 20% | 不可用於改規則，只用於 release 判定 |

另加一個「最新時間區間」的 future-like holdout：

- 不參與規則設計。
- 模擬未來集數與新股票用詞。
- 若以最新集數當正式營運目標，這個集合尤其重要。

### 建議執行量

GPU 成本約：

```text
261 秒/集 × 687 集 ≈ 49.8 GPU 小時
```

這不算低，但在本機 GPU 上是可規劃的一次性批次工作。

建議分兩階段：

#### 階段一：先跑 80～120 集建立管線

分層納入：

- 不同年份／季度。
- 最近集數。
- 歷史集數。
- 股票提及密度高的集數。
- 股票提及稀少的集數。
- 疑似有來賓、廣告、錄音品質變化的集數；是否存在這類集數需以實際資料確認。

目的：

- 驗證對齊器。
- 找出最常見錯誤型態。
- 評估官方稿是否可用。
- 建立人工審核工作量預估。

#### 階段二：在規則與資料格式穩定後跑全 687 集

目標不是立刻把全量用來訓練，而是：

- 建立可重現配對語料庫。
- 統計錯誤長尾。
- 找出常見股票、人物、節目名、產業術語的混淆。
- 建立歷史版本基線。

但 locked test 集不得參與規則生成、人工別名新增、prompt 調整。

# 7. 這個計畫最可能失敗的地方

## Finding 7.1 — 官方稿若非可靠人工稿，整個「標準答案」前提會失效
- **嚴重度：critical**
- **證據：**
  - 使用者明確表示「官方稿本身若也是 ASR 產生的，我方尚未查證」。
- **影響：**
  - 可能把第三方 ASR 的錯誤當成標準答案。
  - 可能只是在追趕另一個模型的錯誤模式。
  - 若官方稿有人工潤稿，本地 ASR 會被懲罰「更貼近音訊」但不貼近編輯稿的情況。
- **具體修法：**
  - 在所有規則開發前，做官方稿品質審計。
  - 不需要先人工驗完整 687 集，但必須建立足夠的 gold audit set。

### 官方稿品質審計方式

抽樣至少包含：

- 隨機集數。
- 股票高密度段落。
- 人名／節目名高密度段落。
- 官方與本地差異很大的段落。
- 官方與本地高度一致的段落。

每個樣本：

1. 人工聽原始音訊。
2. 記錄音訊實際說法。
3. 記錄官方稿。
4. 記錄本地 ASR。
5. 標記錯誤類型：
   - 官方錯。
   - 本地錯。
   - 兩者都錯。
   - 官方潤稿但不違反語意。
   - 音訊不清，無法判定。

若官方稿的股票實體 precision 不足以當銀標準，後續策略要改成：

- 官方稿只用於候選生成，不可直接當 truth。
- 高價值股票 mention 以人工聽音標註為主。
- 建立小而高品質的 gold set 作為最終評估基準。
- 以多個本地 ASR 配置的分歧來做「需人工審核」排序，但不可把模型投票當真相。

## Finding 7.2 — 文字層校正無法解決真正的音訊歧義
- **嚴重度：critical**
- **證據：**
  - `奇鋐 → 奇虹`、`載板 → 載版` 都是同音或近音錯誤。
  - 使用者已點出「某集真的講某個相同字串」的歧義風險。
- **影響：**
  - 規則越多，誤傷率可能越高。
  - 高影響股票訊號可能被錯誤歸到另一檔股票。
- **具體修法：**
  - 保留時間軸。
  - 對高風險候選實施局部重解碼。
  - 無法確認時 abstain，不將其輸入成確定股票訊號。
  - 將「不確定」建模為一級輸出，不要強迫每個 mention 都選一檔股票。

## Finding 7.3 — 替代官方站不等於自主，YouTube 仍是外部依賴
- **嚴重度：major**
- **證據：**
  - 本地管線仍依賴 `yt-dlp` 下載 YouTube。
  - 根本目標是避免第三方來源停更／關站造成斷炊。
- **影響：**
  - 即使不再依賴 `whatmkreallysaid.com`，YouTube 下架、改版、區域限制或影片版本變動仍可能中斷重建能力。
- **具體修法：**
  - 立即快照可取得的資料：
    - 官方逐字稿 raw HTML / raw text。
    - 集數、標題、URL、抓取時間。
    - 音訊檔或可驗證的本地封存格式。
    - 音訊 hash、時長、下載來源。
    - ASR 設定與輸出。
  - 確認內容使用權、網站條款、著作權與本地保存政策；此處目前缺乏事實，需另行確認。

## Finding 7.4 — 模型或設定變動會使既有錯字表失效
- **嚴重度：major**
- **證據：**
  - 錯字模式來自特定 `large-v3-turbo`、特定推論版本與設定。
  - 目前已知 `condition_on_previous_text=False`，後續可能加入 prompt、hotwords、VAD 或其他 decode 參數。
- **影響：**
  - 升級模型後，舊規則可能不再有用，甚至反而誤傷。
- **具體修法：**
  - 每份轉錄記錄完整 `asr_config_hash`。
  - 錯字規則必須指定適用的 config fingerprint。
  - 每次模型、prompt、解碼設定變更，強制重跑 locked test。

# 建議的執行步驟

## Step 0：先做資料保全，不要等演算法完成
1. 批次抓取並保存目前可取得的 687 集官方逐字稿原文與 metadata。
2. 保存 YouTube 音訊、URL、時長與檔案 hash；保存能力與授權／條款需確認。
3. 保存目前已有 EP681–684、EP687 的原始 SRT、`.md`、官方稿與完整 ASR 設定。
4. 所有檔案與資料庫紀錄加入 episode ID、來源 URL、抓取時間、版本 hash。

**驗收條件：**
- 任一已處理集數可在沒有官方網站的情況下重建比對資料。
- 不只保留 `.md`，必須能找到原始 SRT 與音訊時間軸。

---

## Step 1：重構轉錄輸出格式，保住時間軸
1. 修改 `independent_transcribe.py`：
   - `.md` 可以保留，但不能是唯一輸出。
   - 額外輸出 `segments.json` 或保留標準 SRT。
2. 每個 segment 保存：
   - `segment_id`
   - `start`
   - `end`
   - `text`
   - 可取得時的 token / word timestamp
3. 建立 `asr_run_metadata.json`：
   - 模型、版本、語言、beam、VAD、prompt、hotwords、設定 hash。

**驗收條件：**
- 任意本地文本 span 都能回查到對應音訊時間範圍。

---

## Step 2：建立股票實體詞典匯出介面
1. 擴充 `stock_dict.py` 或新增 `stock_entities.py`。
2. 提供可列舉股票實體、canonical 名稱、代碼、別名與格式別名。
3. 將股票、人名、節目名、產業術語拆成不同詞典或不同 entity type。
4. 對別名建立衝突偵測：
   - 一個 alias 對多個股票時，必須回傳多候選，而不是任選一檔。

**驗收條件：**
- 可以列出完整股票實體集合。
- `resolve_text_to_candidates()` 可回傳零、一或多個候選。
- 詞典有版本號與測試案例。

---

## Step 3：以 EP681–684、EP687 實作對齊器 PoC
1. 不改舊 `compare_paragraphs()` 的行為；新增新的 episode-level aligner。
2. 實作：
   - 正規化。
   - 共同 n-gram 錨點。
   - 錨點鏈。
   - 局部字元級動態規劃。
   - 差異 span 與時間軸回填。
3. 輸出可人工閱讀的 HTML / Markdown diff report。
4. 人工檢查至少包含已知案例：
   - `台／臺積電`
   - `奇鋐／奇虹`
   - `貿聯-KY／茂林KY`
   - `載板／載版`
   - `股癌／古來`
   - `謝孟恭／聖夢公`

**驗收條件：**
- 已知案例能被抽成獨立 span，不再只有一個巨大 diff block。
- 每個 span 有對齊信心與本地音訊時間範圍。
- 低品質區段能被標記 uncertain，而非硬配對。

---

## Step 4：建立官方稿品質審計集
1. 從不同時間區間抽樣音訊片段。
2. 優先抽：
   - 股票密集段落。
   - 官方／本地差異最大段落。
   - 已知同音誤聽段落。
3. 人工聽音，產生小型 gold set。
4. 統計：
   - 官方股票實體正確率。
   - 官方人名／節目名正確率。
   - 官方潤稿比例。
   - 官方與音訊不一致類型。

**驗收條件：**
- 有足以判斷官方稿能否作 silver label 的審計報告。
- 未確認前，不得將官方稿當作無條件訓練真值。

---

## Step 5：建立「候選誤聽規則」資料庫，不做全域 replace
1. 從官方股票 mention 中擷取對齊差異。
2. 以 episode 數、出現次數、對齊品質、人工驗證數建立 evidence。
3. 規則分為：
   - `safe_normalize`
   - `entity_link_only`
   - `candidate_only`
   - `rejected`
4. 對高風險或可能碰撞規則，預設 `candidate_only`。

**驗收條件：**
- 沒有任何 `str.replace()` 形式的全域錯字替換。
- 每次校正都有 rule ID、信心、來源與適用 ASR config。

---

## Step 6：建立本地評估器
1. 建立股票 mention precision / recall / F1。
2. 建立 canonical linking accuracy。
3. 建立假股票率與校正誤傷率。
4. 建立簡易方向詞窗口 proxy。
5. 將 episode 切成 train / validation / locked test，並在程式層面防止 test 資料進入規則學習。

**驗收條件：**
- 每次規則或 ASR 設定變更，都能輸出固定格式評估報告。
- 報告能分開看：
  - 原始 ASR。
  - 僅安全正規化。
  - 加候選校正。
  - 加 prompt / hotwords。
  - 局部重解碼後結果。

---

## Step 7：做 prompt / hotwords A/B 測試
1. 先實作 `initial_prompt` / hotwords 的設定透傳與 metadata 紀錄。
2. 測試四組：
   - baseline。
   - 固定節目／人名 prompt。
   - 小型高頻股票詞典。
   - 局部候選詞重解碼。
3. 不測完整股票清單 prompt，除非先有證據顯示不會增加假股票率。
4. 以 locked validation 集比較 precision、recall、假股票率。

**驗收條件：**
- 若 prompt 提升 recall 但使 precision 或假股票率惡化，禁止上線。
- 只有在股票 precision 不下降的前提下，才採用 prompt 策略。

---

## Step 8：擴大轉錄與規則挖掘
1. 先跑 80～120 集確認流程、資料模型與審計成本。
2. 修正對齊與規則流程後，再跑其餘集數。
3. 任何 locked test episode 不得用於：
   - 新增錯字規則。
   - 新增 alias。
   - 調整 prompt。
   - 調整閾值。

**驗收條件：**
- 規則在未參與訓練的 episode 上仍維持目標指標。
- 最近時段 holdout 不出現明顯 precision 崩落。

---

## Step 9：最後才做 Gemini 端到端驗證與取代決策
1. 固定 Gemini prompt、輸入格式、輸出 schema，並記錄實際模型識別資訊。
2. 在 locked test 與 future-like holdout 上比較：
   - 官方稿輸出。
   - 本地校正稿輸出。
3. 對不一致、高影響、虛假股票訊號個案做人工聽音裁決。
4. 只有同時滿足：
   - 股票實體 precision / recall 門檻。
   - 無高風險自動校正誤傷。
   - Gemini 訊號一致率門檻。
   - 人工 gold set 驗證通過。
   
   才能宣告本地稿可取代官方稿作為主來源。

最重要的上線原則：

> **寧可把不確定的股票標記為不確定，也不能把錯股票自信地寫入 PostgreSQL 並計入勝率。**
