## 2. 我對雙審意見的裁決（含我不同意的地方）

### 2-1. 我實測後**下修**了嚴重度的一條

兩邊都說「方向標籤（衰減加權）與括號次數（全歷史）**會**互相矛盾」，Codex 說是正確性 bug，
DeepSeek 說「機制上必然發生」。我用真實資料逐檔驗算：

```
方向相反的檔數: 0        （33 檔全數一致）
原話來源集數 ≠ 最後提及集數: 0 / 33
```

**所以這不是現在算錯，是敘述錯配**——但錯配本身確實**每張卡都在發生**：
台積電印「102多／2空」，而頁面說明寫這是「最近」的比例，實際近 30 天只有 4 集。
我照這個定性去改（拆時間窗、標清楚），而不是照「正確性 bug」去改（改算法）。

### 2-2. 兩邊有衝突、我做了取捨的一條

- **Codex**：第二頁應該補「常駐短圖例」，因為分數量尺只寫在可關閉的 onboarding 裡。
- **DeepSeek**：第二頁 onboarding 可關閉是**對的**、不該改，因為已經有常駐黃框補位。

我兩邊都採：**不動 onboarding 的可關閉性**（DeepSeek 對），但**把量尺說明搬進常駐黃框**（Codex 對）。
這樣關掉 onboarding 之後，最大的那個數字仍然有單位。

### 2-3. 我沒有採納的建議（留給你裁決，不是忘記）

| 建議 | 來源 | 我為什麼沒做 |
|---|---|---|
| 產生靜態搜尋索引 + Web Worker | Codex | 按鈕觸發已經解掉「無意間觸發 35MB」這個急迫問題；建索引是另一個工程量級，且會改變產生流程與部署內容，應該由你決定要不要投入 |
| 原話預設收合 | Codex | 跟你對第一頁的裁決（「說明要更詳細不是更精簡」）方向相反，而且原話是這頁最有價值的證據。**這條我判斷不了你的偏好，列為待裁決** |
| 第三頁預設只顯示最近 30 集 + 載入更多 | 兩邊 | 685 列渲染實測沒有效能問題，而標題搜尋現在是即時的，已能快速定位。加分頁反而多一層操作 |
| 搜尋命中顯示前後文 snippet ／ 高亮 | DeepSeek | 有價值，但工程量不小，且要處理跳脫。列為下一輪候選 |
| 引用句加方向標記（↑／↓） | DeepSeek | 引用句是「最近一次提及」，跟卡片的加權方向不是同一個東西，加箭頭反而製造新的錯配。**刻意不做** |

## 3. 逐項改動與證據

### 3-1. 第二頁：方向與次數拆開

**改前**（真實畫面）
```
台積電  台股 2330.TW
偏多共識（102多／2空）          ← 紅色
                                        64.55
                                        關注度
最後提及 2026-08-05（EP685）    近30天提及：EP685、EP683、EP681、EP680
```

**改後**（真實畫面）
```
台積電  台股 2330.TW
↑ 近期偏多                     ← 中性灰（沿用第一頁方向 chip 慣例）
                                   64.55 / 100
                                   近期討論熱度
最後提及 2026-08-05（EP685）（6 天前）      歷史累計 128 次提及（102 多／2 空）
近30天提及：EP685、EP683、EP681、EP680      ← 每個 EP 都是連結
```

同時修掉 onboarding 那句錯的說明（原文：「『偏多共識／偏空共識』看的是最近多空次數比例」）。

### 3-2. 第二頁：量表

常駐黃框新增一句：分數 **0–100**（提及次數 × 信心等級，再依距今天數衰減），**不是報酬率也不是勝率**；
並顯示當期榜首分數（目前 64.55），讓訪客有相對尺標。

### 3-3. 第二頁：其餘

- `近30天提及` 超過 8 集不再靜默截斷，改顯示「…等 N 集」
- 補「距今幾天」與「歷史累計 N 次提及」（`age_last`／`total_mentions` 原本算了卻沒顯示）
- 搜尋範圍納入原話（原本只有名稱＋代號，打「漲價」「AI」一定落空）
- 搜尋框補 `<label>` 與 `aria-label`；header 的站名改成 `<h1>`

### 3-4. 第三頁：搜尋改兩段式（實測）

```
打字「台積電」→ 17 / 685 集標題符合（只下載 1 個檔案）
按「連內文一起搜」→ 進度：110/685 → 230/685 → 350/685 → 600/685
                 → 446 / 685 集符合「台積電」（含內文命中 429 集）
```
下載期間出現「取消」按鈕；並行度從 685 降到 8。

### 3-5. 第三頁：錯誤分類（對照組實測）

| 情境 | 判定 | 使用者看到 |
|---|---|---|
| 要求不存在的 EP99999（真 404） | `missing` | 「這集逐字稿檔案缺失…不是網頁的錯誤。」 |
| 把 `fetch` 換成必定 reject（模擬斷網） | `network` | 「載入失敗：連不到逐字稿檔案（網路或伺服器問題），請稍後再點一次。**這不代表這集沒有逐字稿**。」 |

兩段文字實測不同。網路失敗**不標記 loaded**，所以再點一次會重試（原本失敗後永遠卡住）。

### 3-6. 第三頁：深連結（端到端實測）

用正式站的檔名（`_site_preview/` 比照 workflow 的 `index.html`／`attention.html`／`transcripts.html`）：

```
attention.html 上 93 個 EP 連結，href = transcripts.html?ep=685
  → 開啟後 tr-body-685 自動展開，全文 21,109 字，aria-expanded=true，捲動到位並高亮
```

### 3-7. footer 不再空口承諾

原本寫死「共 685 集逐字稿」。改成實際數 `transcripts_data/` 有幾個檔案：
目前顯示「共 685 集節目，逐字稿全數齊備」；缺檔時會顯示「其中 X 集有逐字稿、Y 集檔案缺失」。
**對照組實測**兩個分支都會真的變（不是永遠印齊備）。

### 3-8. `attention.py` 靜默丟棄 → 出聲 + 第二來源

三組對照：

| 組 | 條件 | 結果 |
|---|---|---|
| A | episodes.json 完整 | 33 檔，榜首最後提及 **EP685** |
| B | episodes.json 停在 EP680 **＋新救援** | 33 檔，**EP685**（救回來了） |
| C | episodes.json 停在 EP680，**拔掉救援**（＝改動前行為） | **28 檔，停在 EP680** ← 精準重現今晚踩到的狀況 |

C 組同時噴出警告，列出 `EP685(10筆)、EP684(3筆)、EP683(1筆)、EP682(5筆)、EP681(4筆)`。

> 第二來源用的是 `signals.entry_date`（`performance.py` 依 episodes.json **真實上架日**回填的快照），
> **沒有**動用 `analysis_date`——那條禁令是任務檔明文拍板的，這次沒有放寬。

## 5. 還沒做／你可能不同意的地方

1. **原話預設展開還是收合**：Codex 建議收合，我沒改（見 2-3）。
2. **靜態搜尋索引**：真正的解法，但工程量與部署內容都要改，等你決定。
3. **第二頁沒有「這檔過去準不準」的直接入口**：現在只有黃框裡一句「請回主報告」。
   要做成「點標的 → 跳到第一頁該檔履歷」需要第一頁支援 deep link，跨兩頁，我沒自作主張。
4. **這三頁的字級與間距沒有統一**：第二頁 `filter-btn` 是 `5px 12px`、第一頁是 `4px 10px`，
   兩份 CSS 各自定義。沒動，因為改共用樣式會同時影響三頁，風險大於收益。
